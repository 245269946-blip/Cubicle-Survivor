# Demo V1 核心修改意见纲领

这份文档是后续所有 Demo V1 修改的回转检查基准。每次改武器、战斗、UI、关卡、经验、材料、卡槽或工坊，都必须回到这里检查一次：玩家是否真的能在战斗里看见 Build 差异，是否真的能从升级中获得下一步探索欲。

## 一句话目标

每一次 Build 决策，下一场战斗 10 秒内必须看得出来。

如果看不出来，就优先加强战斗反馈、降低解释成本、推迟开放、合并机制，或者删除这条机制。不要靠更多文字解释一个玩家玩不到的系统。

## 核心判断标准

### 1. 选择必须形成闭环

每个重要选择都要完成三步：

- 选择前：玩家知道这次会改变哪把武器、哪种攻击方式、哪项短板。
- 选择后：系统用短反馈确认变化，不写长说明。
- 下一场战斗：玩家能立刻看到攻击形态、触发频率、范围、命中过程或留场效果发生变化。

任何只停留在面板文字、数值加成、羁绊说明里的改动，都不能算完成。

### 2. 战斗反馈优先级高于决策复杂度

当前最大风险不是机制不够多，而是机制太多但战斗差异不够明显。

修改优先级：

1. 战斗中是否看得出。
2. 选择页是否能预期到。
3. 工坊/卡槽是否能解释清楚。
4. 复盘是否能确认这一局发生了什么。

不要反过来先堆卡牌、词条、阶段、商店商品，再让战斗勉强承接。

### 3. 武器母题必须压过部门加成

玩家选择的不是“哪个部门加成更好”，而是“我要把这把办公工具养成什么荒诞职场武器”。

每把武器必须先确认母题：

- 马克笔：画线、贯穿、分裂。
- 保温杯：蓄热、沸点、释放。
- 即时贴：落点、布阵、连线成区。

部门形态只能扩展母题，不能把武器改成另一把武器。代表部门要把母题推到别人无法模仿的极致，其他部门做有边界的变体。

### 4. UI 只回答当前页面真正的问题

不同页面的信息职责不能打架。

- 战斗页：只服务即时操作和动态规划。重点是血量、关卡目标、倒计时/剩余、材料、当前主武器形态、关键状态。
- 武器选择页：回答“这把武器怎么打怪”。
- 工牌选择页：回答“同一把武器会被这个部门改造成什么攻击形态”。
- 升级页：回答“这次成长如何影响当前主武器形态”。
- 卡槽页：回答“覆盖/追加前后，当前形态具体多了什么、少了什么”。
- 工坊页：回答“我用材料补强当前主武器的什么短板或机制”。
- 复盘页：回答“我这局最终是什么形态，主要伤害来自哪里，下一局可以尝试什么变化”。

页面里不服务当前问题的信息，要降级、折叠、延后或删除。

- 购买页与选择页不是说明书：单张卡默认只保留名称、立刻结果，以及最多一条未来或协同提示。
- 如果首眼需要连续读三段文字才能决定，说明信息分层失败；优先删除或延后，不靠缩小字号硬塞。

### 5. 不允许用文字弥补体验缺失

长文案、叙事梗、路线推荐都不能替代战斗反馈。

文案规则：

- 标题可以有职场味。
- 副文必须直说机制。
- 单张卡默认不超过 2 条结果导向信息；只有复盘或主动展开详情可以更长。
- 不写“推荐你走某路线”这种强指令。
- 多写“会变成什么攻击方式”“下一场你会看到什么”。

如果一条机制必须靠很多文字才能让人懂，优先重做机制表现，而不是继续扩写说明。

### 6. 经验和材料是副线，但必须服务主线

经验和材料不能变成与主武器 Build 平行的另一套噪音系统。

- 经验：全程独立结算，满了就给通用成长或当前形态小成长。选项必须说明对当前主武器有什么影响。
- 材料：用于工坊，补强当前主武器、容错、短板或当前阶段允许的副线。
- 工坊：不能越权提前提供第二部门、跨武器或跳阶段内容。
- 卡槽：不能只是五个一次性孔位。填满后要允许追加强化，但必须显示前后变化。

副线存在的意义是让主武器 Build 更可见、更顺、更有调整空间。

### 7. 阶段节奏服务学习，不服务塞内容

当前 5 阶段主线是体验骨架：

1. 初始武器理解。
2. 工牌形态定型。
3. 转正后主形态强化。
4. 第二部门初级形态叠加。
5. 跨技能学习，副武器只做辅助。

每个阶段都要让玩家有时间玩懂当前层级。不要因为系统已实现就提前塞给玩家。阶段奖励发生在阶段结束后，不发生在阶段刚进入时。

### 8. 视觉资源必须是可实装资产，不是概念拼贴

最终 active UI 和核心战斗 VFX 需要使用 image2 输出或可复用的 raster asset。

视觉规则：

- 2D 平面窗口优先，不把 3D 透视图硬塞进选择界面。
- 办公室感优先，霓虹是点缀，不要整体科幻化。
- 卡框、按钮、状态栏、横幅、材料条、复盘纸张等可见主体都应逐步资产化。
- CSS 负责布局和状态，不负责画主体外观。
- 任何新视觉必须检查：文字可读、尺寸匹配、攻击范围和特效范围一致。

旧探索图可以保留为 reference，但不能默认当 active UI。

### 9. 自动测试只能证明能跑，不能证明好玩

测试必须保留，但不能误以为测试通过就代表体验完成。

自动测试证明：

- 不报错。
- 流程不死锁。
- 机制事件触发。
- 16 关能跑通。

体验验收还必须人工看：

- 选择后下一场 10 秒内是否能看出变化。
- 怪物密度是否让新形态有发挥空间。
- 特效大小是否符合人物、敌人、范围。
- 页面是否一眼知道该看哪里。
- 玩家是否能在失败中看到“下次我想换一种构筑试试”。

## 每次修改前必须问

- 我这次改动服务的是哪一个阶段？
- 它改变的是哪把主武器的哪种战斗方式？
- 玩家在下一场战斗中会看到什么新东西？
- 如果玩家不读说明，他能不能猜到这个选择的意义？
- 这个信息应该出现在当前页面吗，还是应该延后/折叠/删除？
- 它是否破坏了经验、材料、卡槽、工坊作为副线服务主线的关系？

## 每次修改后必须验收

- 首屏没有乱码、旧分类词、旧占位 UI。
- 从开始游戏到第一关战斗，倒计时和 warmup 正常推进。
- 选择武器后能看到该武器基础攻击动词。
- 选择工牌后，下一关战斗方式明显变化。
- 卡槽覆盖/追加有前后对比，并且战斗中能看到对应变化。
- 工坊商品只服务当前主武器形态或阶段允许的副线。
- 1280x720 下材料数、继续按钮、主要选择按钮不被遮挡。
- `node test-runner.js` 和 `node demo-qa.js` 通过。

## 红线

- 不再用“文字解释很多但战斗几乎一样”的 Build。
- 不再用“推荐路线”替代玩家自己理解构筑。
- 不再让工坊、材料、卡槽抢主线阶段节奏。
- 不再把未开放阶段内容提前塞进商品或选择池。
- 不再把视觉概念图直接当实装 UI。
- 不再只修用户指出的单点问题，必须检查相邻系统是否被牵连。
